## Введение

Цель работы — изучить основные принципы разработки и развёртывания веб-приложений на языке Python с использованием микрофреймворка Flask. Практической задачей является создание веб-приложения для принятия файлов от пользователей, генерации изображений и графиков, защиты формы от автоматических запросов, а также настройка автоматической проверки и развёртывания приложения на сервере.

Основные задачи:

- Разработать веб-приложение на Flask, позволяющее пользователю загружать исходное изображение и задавать параметры его обработки.
- Реализовать обработку изображения средствами библиотеки Pillow: нанесение вертикального, горизонтального или комбинированного креста заданного пользователем цвета и толщины, а также опциональное нанесение отметки даты и времени создания изображения.
- Реализовать построение гистограмм распределения цветовых каналов R, G и B для исходного и обработанного изображений с использованием библиотеки Matplotlib.
- Реализовать защиту формы от автоматических запросов с помощью капчи и механизма сессий Flask.
- Организовать отображение исходного изображения, результата его обработки и построенных гистограмм в веб-интерфейсе.
- Настроить непрерывную интеграцию (CI) с использованием GitHub Actions для автоматической проверки установки зависимостей и корректности импорта приложения.
- Выполнить развёртывание разработанного веб-приложения на сервере с использованием WSGI-сервера Gunicorn.

Flask представляет собой микрофреймворк для разработки веб-приложений на Python и предоставляет механизмы маршрутизации HTTP-запросов, шаблонизации с использованием Jinja2 и работы с пользовательскими сессиями. Для обработки растровых изображений в работе применяется библиотека Pillow, позволяющая загружать, изменять и сохранять изображения различных форматов. Построение гистограмм распределения цветовых каналов выполняется средствами библиотеки Matplotlib с использованием NumPy для быстрой векторной обработки пиксельных данных.

Для запуска приложения в серверной среде используется Gunicorn — WSGI-сервер, предназначенный для обслуживания Python-веб-приложений. Дополнительно применяется механизм непрерывной интеграции: GitHub Actions автоматически устанавливает зависимости и проверяет корректность импорта приложения при изменении исходного кода.

Таким образом, выполнение лабораторной работы позволяет изучить базовый цикл разработки веб-приложения: от обработки пользовательского ввода и реализации прикладной логики до автоматической проверки и развёртывания приложения на сервере.

Структура каталога веб-приложения web-services-course/labs/lab1/ организована следующим образом. Файл app.py содержит основной программный код приложения, включающий определение маршрутов (routes) и реализацию логики обработки запросов. Файл requirements.txt содержит перечень программных зависимостей, необходимых для функционирования приложения. Файл Procfile определяет команду запуска приложения при развёртывании на PaaS-платформе с использованием сервера gunicorn. Файл .env предназначен для хранения переменных окружения (в частности, секретного ключа SECRET_KEY) и исключён из системы контроля версий git в целях безопасности. Файл .gitignore содержит перечень исключений для git, в который входят виртуальное окружение, файлы кэша, загруженные пользователем файлы и файл .env. Каталог templates/ содержит HTML-шаблоны приложения: файл index.html реализует форму для загрузки изображения и ввода параметров обработки, а файл result.html представляет собой страницу отображения результата обработки.

Каталог static/ содержит статические файлы приложения и включает две подпапки: uploads/ — для хранения исходных изображений, загруженных пользователем, и generated/ — для хранения сгенерированных изображений с нанесённым крестом (результата обработки).

## 2 ОПИСАНИЕ ХОДА ВЫПОЛНЕНИЯ РАБОТЫ

Создан проект на базе микрофреймворка Flask. Структура каталога включает основной модуль app.py, каталог шаблонов templates/, каталог статических файлов static/ (с подкаталогами uploads/ и generated/), виртуальное окружение venv и файл зависимостей requirements.txt (Flask, Pillow, matplotlib, numpy, gunicorn, python-dotenv). Секретный ключ приложения (SECRET_KEY) вынесен в переменные окружения и загружается модулем python-dotenv из файла .env.

Реализована форма загрузки изображения (templates/index.html), позволяющая выбрать файл в формате PNG/JPG/JPEG/BMP и задать параметры отрисовки креста: ориентацию (вертикальный, горизонтальный либо оба направления одновременно), цвет линии посредством элемента `<input type="color">` и толщину линии в пикселях (числовое поле с ограничением диапазона 1–200).

Реализована защита формы от автоматической отправки при помощи капчи. При каждом GET-запросе к маршруту / функция new_captcha генерирует случайный пример на сложение двух однозначных чисел и сохраняет правильный ответ в серверной сессии (session["captcha_answer"]). При обработке формы (маршрут POST /process) введённое пользователем значение сравнивается с ожидаемым ответом; в случае несовпадения либо отсутствия ответа в сессии пользователь перенаправляется обратно на форму с флеш-сообщением об ошибке.

Обработка изображения реализована средствами библиотеки Pillow. Функция draw_cross приводит изображение к цветовой модели RGB, вычисляет координаты центра и с помощью ImageDraw.rectangle отрисовывает один или два прямоугольника заданной толщины и цвета, формирующих крест выбранной ориентации. Загруженные и обработанные изображения сохраняются на диск с уникальными именами (на основе uuid4), что исключает конфликт файлов разных пользователей.

Построение гистограмм распределения значений каналов R/G/B реализовано функцией histogram_png_base64 средствами библиотеки Matplotlib (бэкенд Agg, без графического дисплея). Изображение переводится в массив NumPy (np.asarray), для каждого канала строится гистограмма распределения яркости (256 интервалов), после чего график кодируется в формат PNG в буфере памяти и представляется в виде строки Base64 для последующего встраивания в HTML-страницу без сохранения промежуточных файлов на диск. Гистограммы строятся отдельно для исходного и обработанного изображений.

Страница результата (templates/result.html) отображает исходное и итоговое изображения, а также соответствующие им гистограммы, расположенные попарно в две колонки при помощи CSS flexbox-вёрстки.

Настроена система непрерывной интеграции средствами GitHub Actions (файл .github/workflows/ci.yml): при каждом push в ветки web_services_course/main, а также при создании pull request в main, выполняется установка зависимостей проекта из requirements.txt и проверка корректности импорта модуля app.py.

Устранена проблема зависания маршрута /process на изображениях большого разрешения: функция построения гистограммы переписана с поэлементного обхода пикселей (list(image.getdata())) на векторные операции NumPy (np.asarray(...).ravel()), что на порядки ускорило подсчёт значений каналов; дополнительно добавлен предварительный даунскейл входного изображения при превышении стороны в MAX_DIMENSION = 4000 пикселей (функция downscale_if_huge); таймаут воркера Gunicorn увеличен до 60 секунд (--timeout 60 в Procfile и systemd-юните) вместо стандартных 30 секунд.

Реализована опциональная отметка даты и времени создания изображения. В форму загрузки добавлен флажок «Добавить дату и время создания на картинку»; при его установке функция draw_timestamp наносит на итоговое изображение текущую дату и время сервера в формате ДД.ММ.ГГГГ ЧЧ:ММ:СС в правом нижнем углу с тёмной полупрозрачной подложкой для читаемости текста на любом фоне. Нанесение выполняется после отрисовки креста и до сохранения результата на диск, поэтому на гистограмму итогового изображения штамп не влияет отдельно — гистограмма считается уже с готового результата.

Настроен запуск приложения в производственном режиме через WSGI-сервер Gunicorn (файл Procfile: web: gunicorn --timeout 60 app:app); выполнено развёртывание приложения на VPS-сервере (описание процесса — см. раздел 4).

## 4 РАЗВЁРТЫВАНИЕ НА СЕРВЕРЕ

Приложение развёрнуто на VPS (Ubuntu, Yandex Cloud), на котором уже эксплуатируется другой проект (nginx на 80 порту). Чтобы не затрагивать существующий сервис, лабораторная работа вынесена на отдельный порт и запущена как самостоятельный systemd-сервис — без изменения конфигурации nginx.

### 4.1 КОМАНДЫ РАЗВЁРТЫВАНИЯ

```bash
# 1. Клонирование только нужного каталога репозитория (sparse-checkout)
git clone --filter=blob:none --sparse https://github.com/julmedvedeva/tusur.git tusur-web
cd tusur-web
git sparse-checkout set web_services_course/labs/lab1

# 2. Виртуальное окружение и зависимости
cd web_services_course/labs/lab1
sudo apt install python3.10-venv
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

# 3. Файл окружения
echo "SECRET_KEY=$(python3 -c 'import secrets; print(secrets.token_hex(16))')" > .env
```

Файл .env создаётся вручную непосредственно на сервере (см. шаг 3) и в репозиторий не попадает — он исключён в .gitignore. Значение SECRET_KEY, используемое в проде, отличается от значения при локальной разработке и нигде, кроме сервера, не хранится.

systemd-юнит /etc/systemd/system/lab1.service:

```ini
[Unit]
Description=TUSUR lab1 flask app
After=network.target

[Service]
User=ubuntu
WorkingDirectory=/home/ubuntu/tusur-web/web_services_course/labs/lab1
Environment="PATH=/home/ubuntu/tusur-web/web_services_course/labs/lab1/venv/bin"
ExecStart=/home/ubuntu/tusur-web/web_services_course/labs/lab1/venv/bin/gunicorn --workers 2 --timeout 60 --bind 0.0.0.0:8001 app:app
Restart=always

[Install]
WantedBy=multi-user.target
```

Запуск сервиса:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now lab1
sudo systemctl status lab1
```

Приложение доступно по адресу http://93.77.183.153:8001/. Существующий сервис на порту 80 (nginx, второй проект) не затронут.

## 5 ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

### 5.1 Теория CI/CD

CI (Continuous Integration, непрерывная интеграция) — практика, при которой каждое изменение кода автоматически проверяется на общем сервере: устанавливаются зависимости, запускаются линтеры и тесты, проверяется сборка. Цель — обнаруживать ошибки интеграции сразу после коммита, а не после того, как несколько разработчиков долго работали изолированно и затем с трудом сливали ветки.

CD расшифровывается двояко:

- Continuous Delivery (непрерывная доставка) — после прохождения CI сборка автоматически подготавливается к выпуску (собирается артефакт/образ), но развёртывание в продакшн выполняется вручную по решению человека;
- Continuous Deployment (непрерывное развёртывание) — тот же процесс, но без ручного шага: версия, прошедшая все проверки, автоматически выкатывается в продакшн.

В данной работе настроен только этап CI (GitHub Actions, файл .github/workflows/ci.yml): при push и pull request устанавливаются зависимости и проверяется корректность импорта app.py. Этап CD не автоматизирован — развёртывание на VPS (раздел 4) выполняется вручную по SSH.

### 5.2 Преимущества HTTP/2 перед HTTP/1.1

HTTP/1.1 — текстовый протокол, в котором на одном TCP-соединении в конкретный момент времени обрабатывается один запрос-ответ; механизм keep-alive позволяет переиспользовать соединение, но не даёт параллелить запросы внутри него, из-за чего возникает проблема Head-of-Line blocking на уровне приложения, а браузеры вынуждены открывать несколько параллельных TCP-соединений к одному хосту. HTTP/2 устраняет эти ограничения и даёт следующие преимущества:

- мультиплексирование — несколько запросов и ответов передаются по одному TCP-соединению параллельно и независимо друг от друга, без очереди из-за одного медленного запроса;
- бинарный протокол — данные передаются кадрами (frames) в бинарном виде, а не текстом, что ускоряет разбор сообщений;
- сжатие заголовков по алгоритму HPACK — повторяющиеся заголовки (cookie, user-agent и т. п.) не передаются в каждом запросе заново;
- server push — сервер может заранее отправить клиенту ресурсы, которые тот с высокой вероятностью запросит следом (например, CSS вместе с HTML);
- приоритизация потоков — клиент может указать, какие запросы важнее, и сервер обрабатывает их в первую очередь.

В результате HTTP/2 снижает задержки при загрузке страниц с большим числом ресурсов и эффективнее использует одно соединение, не требуя приёмов вроде объединения файлов или CSS-спрайтов, применявшихся при работе с HTTP/1.1.

### 5.3 Проблема GIL в Python

GIL (Global Interpreter Lock, глобальная блокировка интерпретатора) — механизм эталонной реализации Python (CPython), который позволяет только одному потоку исполнять байт-код Python в любой момент времени, даже если процесс многопоточный и в системе доступно несколько ядер CPU. GIL существует для упрощения управления памятью CPython: счётчики ссылок объектов увеличиваются и уменьшаются не атомарно, и без глобальной блокировки при обращении к одним и тем же объектам из разных потоков возникали бы состояния гонки.

Следствия наличия GIL:

- многопоточность в Python не даёт прироста производительности на CPU-bound задачах (вычисления, обработка изображений в чистом Python и т. п.) — потоки по очереди передают друг другу GIL и фактически выполняются не параллельно;
- на I/O-bound задачах (сетевые запросы, чтение файлов, ожидание ответа от базы данных) многопоточность остаётся полезной, поскольку во время ожидания операции ввода-вывода поток освобождает GIL, и в это время может выполняться другой поток;
- чтобы реально распараллелить вычисления между несколькими ядрами процессора, используют модуль multiprocessing (отдельные процессы, у каждого свой интерпретатор и своя блокировка GIL) либо переносят тяжёлые вычисления в C-расширения (например, NumPy).

В данной работе GIL напрямую не является ограничением: Flask-приложение обслуживается сервером Gunicorn с несколькими процессами-воркерами (--workers 2), а не потоками, поэтому запросы разных пользователей обрабатываются параллельно на уровне операционной системы, в обход ограничения GIL.

### 5.4 Отметка даты и времени на изображении

По заданию реализована возможность добавления даты и времени создания на формируемое изображение по желанию пользователя. Реализация описана в разделе 2: в форму (templates/index.html) добавлен флажок «Добавить дату и время создания на картинку»; при его установке новая функция draw_timestamp (app.py) наносит на итоговое изображение текущую дату и время сервера (datetime.now()) в формате ДД.ММ.ГГГГ ЧЧ:ММ:СС в правом нижнем углу, на тёмной полупрозрачной подложке, обеспечивающей читаемость текста независимо от цвета фона изображения. Функция вызывается после отрисовки креста, поэтому штамп попадает и на итоговое изображение, и на его гистограмму. Листинг приведён в Приложении А (файл app.py, функция draw_timestamp).

## Заключение

В ходе выполнения лабораторной работы было разработано веб-приложение на языке Python с использованием микрофреймворка Flask. Реализованы загрузка и обработка пользовательских изображений, нанесение креста с заданными параметрами, опциональное нанесение отметки даты и времени создания изображения и построение гистограмм распределения цветовых каналов для исходного и обработанного изображений. Для защиты формы от автоматических запросов реализована капча с использованием механизма сессий Flask. Настроена непрерывная интеграция с помощью GitHub Actions, обеспечивающая автоматическую установку зависимостей и проверку корректности импорта приложения. Устранена проблема зависания обработки больших изображений за счёт векторизации гистограммы средствами NumPy и предварительного даунскейла. Приложение развёрнуто на VPS и запущено через Gunicorn как отдельный systemd-сервис. Таким образом, поставленная цель достигнута, а основные этапы разработки, проверки и развёртывания веб-приложения освоены на практике.
